## 3. 已定位问题与当前修复状态

### 3.1 Navigation 在 hydration 期间冻结旧 TurnIndex

当前 `bootstrap.navigate()` 在导航开始时把：

```js
turns: index.getOrdered()
```

作为一次性数组传给 `NavigationAdapter`。随后 Adapter 在整个导航生命周期里冻结：

- `targetOrder`
- `orderById`
- known turn ordering

但 Local Work 加载更早历史时会继续执行 UUIDv7 reindex。真实案例：

```text
点击时：某稳定 Turn 显示为 Q30
完整历史挂载后：同一 stable UUID 变为 Q48
```

当前 `开始 Vivaldi Faithful 项目规划` 的持久 Timeline Cache 已有 48 条；尾部同一 stable UUID 的最终 order 为 47，即 Q48。

**结果：** Timeline 已经更新到新全局顺序，正在运行的 Navigation 仍拿旧 Q 坐标继续找路。这可以解释：

- 目标已经出现在屏幕上仍显示“正在定位 Q30”。
- Earlier navigation 在 Q21 一带出现跳动/方向异常。
- 手动把历史全部加载后 Q1 ↔ Q46/Q48 可正常工作，而部分加载状态更容易失败。

**本轮已实现，待实机验收：** Navigation 现在以 stable target UUID 为唯一固定目标，通过动态 `getTurns()` 获取当前 TurnIndex；每轮 hydration 以及等待期间的 reindex 都会刷新 targetOrder / orderById，pending Q 编号和失败 Toast 也使用最新 order。

### 3.2 Conversation identity 优先级可能选错 Work Local Thread

当前 `ConversationAdapter.getConversationIdentity()` 顺序为：

```text
route
→ selected ChatGPT conversation
→ selected Local thread
→ DOM fallback
```

真实 Work/Codex Desktop 里可能同时残留 ChatGPT sidebar 的 selected/aria-current 痕迹和明确的 Local Thread selected/active 状态。

Local Thread 的 Timeline Cache 可能已经完整，例如 48 条；如果启动时误选 ChatGPT identity，就不会加载 `local:<UUID>` 的完整 cache，只会从当前局部 DOM 重新长出 30、33、46、48 条。

这与以下现象一致：

- 重启后 Questions 又只有约 30 条。
- 继续手动加载历史后 Q 总数不断增加。

**本轮已实现，待实机验收：** identity 优先级已改为：

```text
route（明确会话 route）
→ stable selected/active Local Thread
→ selected ChatGPT conversation
→ DOM fallback
```

并新增 Local 与 ChatGPT 同时有 selected 痕迹时 Local stable identity 必须胜出的回归。

### 3.3 当前无参 `Codex++ saveNow()` 持久化方案无效且有误写风险

当前 WIP 在 verified navigation success 后调用：

```js
window.__codexThreadScrollHandlers?.saveNow?.()
```

真实运行时证明 Codex++ 的 `activeSessionId` 可以滞后于 GPT TalkEnhancer 当前 Conversation。

已观察到：

```text
GPT TalkEnhancer 当前 conversation = ChatGPT conversation A
Codex++ activeSessionId            = 另一个 Local Work UUID
```

无参 `saveNow()` 默认使用 Codex++ 自己的 activeSessionId / activeScroller，因此可能把当前页面位置写进错误 Thread。已见过错误/无效的 Restore entry：

```text
top          = 0
scrollHeight = 0
clientHeight = 0
```

因此之前“verified success 后无参 saveNow 可修复重启恢复旧 Q31”的结论已废弃。

**本轮已实现，待实机验收：** 已删除 verified success 后的无参 `saveNow()`。仅当：

- identity 为 stable `sidebar-local`；
- conversation 仍 current；
- exact scroll container 有效且 `scrollHeight/clientHeight > 0`；

才显式调用：

```js
saveNow(explicitLocalSessionUuid, exactScrollContainer)
```

ChatGPT identity 暂不做 Restore 写入，除非以后得到可靠 session mapping。失败 / superseded 不保存。

## 4. 修复前真实可复现症状（用于实机回归）

1. 重启 Codex 后，之前明明定位到后段，重新打开会话仍可能恢复到旧 Q31 左右。
2. 部分加载的长 Work：从后段定位 Q1，常在 Q21 附近出现上下跳动/失败。
3. 同一会话手动把历史完整加载后，Q1 ↔ 最后一问通常正常。
4. Local Work 的 Q 总数可随更早历史挂载从约 Q30 增长到 Q46/Q48；导航若在增长过程中启动，旧 targetOrder 会失真。
5. 已经在屏幕上的目标仍可能保持 pending 文案，和动态 reindex/旧 targetOrder 有关，不应先用更长 Toast 延迟掩盖。

## 5. 已排除 / 已删除的实验路线

以下为 0.4.4 调试过程中试验过、当前源码已不保留的路线。除非出现新的直接运行时证据，不应重新引入：

- Earlier Boundary Pulse
- Top-Latch
- Mutation Repin / Mutation Latch
- Quiet Final Wait
- short-vs-long Earlier 两套状态机
- `workWheelMaxStalls`
- `workLongHistoryThreshold`
- periodic 1px boundary pulse
- periodic top-edge rewrite

历史经验：继续叠滚动策略只会扩大状态机。0.4.4 已通过 identity / dynamic TurnIndex / explicit restore session / tail verification 的自动与实机回归，不再继续叠加 wheel 策略。

## 6. 最终验收结果

1. **Conversation Identity：PASS**。stable selected/active Local Thread 优先于残留 ChatGPT sidebar selection；重启后完整 Local Timeline Cache 可直接恢复。
2. **Dynamic Navigation Index：PASS**。stable target UUID 固定，`getTurns()` 动态刷新 current TurnIndex 与 targetOrder/orderById；实机已观察 Q48 → Q63 等动态重编号仍能保持正确目标。
3. **Earlier Navigation：PASS**。长 Work 从后段到 Q1 可持续 hydration；此前 Q21 附件区域往返跳屏、Q4 → Q1 卡住等问题本轮未再复现。
4. **Restore Persistence：PASS**。无参 `saveNow()` 已撤除；stable Local verified success 显式保存 exact session UUID + exact scroll container，重启后未再复现旧 Q31/Q54 恢复。
5. **Last Turn Tail Verification：PASS**。动态最后一问位于 column-reverse newest/tail 物理边界且真实可见时可直接 verified，不再持续显示定位中。
6. **Tail Fast Path：PASS / 保留**。Q1 → 当前最后一问在 virtualizer 已有足够 scroll extent 时可瞬间跳到 tail；否则按宿主加载节奏渐进推进。两种行为均为预期，不强制统一动画。
7. **已知低优先级 UI consistency**：tail endpoint 主体已正确到最后一问时，ActiveTracker / Timeline active marker 偶尔仍显示前一问（例如 Q62 而主体已在 Q63）。不影响导航结果，不阻塞 v0.4.4，后续版本单独处理。
