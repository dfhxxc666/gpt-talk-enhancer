# GPT TalkEnhancer v0.6 Architecture Reset Review

状态：SECOND-PASS / ADVERSARIAL REVIEW
日期：2026-09-20
评审对象：V0.6-ARCHITECTURE-RESET.zh-CN.md

## 1. 评审方法

第一遍方案从“如何解决当前技术问题”出发。

本次换一个角度：

> 假设这份方案半年后失败，最可能是哪些决策导致的？

重点审查：

- 是否只是把复杂度从一个文件搬到三个系统。
- 是否过度相信官方 Plugin。
- 是否为了架构纯洁牺牲当前可用功能。
- 是否把“无法知道完整历史”包装成架构原则逃避产品需求。
- 是否存在无法回滚的数据迁移。
- 是否把 Work 已验证成果一起推倒。

## 2. 最大反对意见：Hybrid 可能更复杂

风险：

    Core
    + Host Injector
    + Plugin
    + MCP
    + Hooks
    + optional UI

很容易比今天更难维护。

### 修正

Plugin 不得成为 v0.6 的关键路径。

实施顺序必须是：

    Safety
    -> Core/Host boundary
    -> Thin Injector
    -> Work bridge
    -> Plugin PoC

而不是三套系统同时开工。

如果 Plugin PoC 不能实际减少 Host Injector 职责，就保持可选工具层。

结论：原方案保留，但降低 Plugin 的架构地位。

## 3. 第二个反对意见：不再自动加载完整 Chat，会不会让 Timeline 退化

这是最真实的产品代价。

用户期待 Timeline 能看到完整问题列表，而不是“当前已知 24Q”。

但现在的 102Q -> 5Q 说明：

> 为了自动追求完整，宁可破坏已知正确数据，是更严重的失败。

### 修正

不取消“完整 Timeline”目标，只改变获取方式：

优先级：

1. 官方稳定数据源/API。
2. 官方 marker 可验证覆盖。
3. 用户显式加载历史。
4. 安全的增量缓存。

后台自动滚动整页只能作为最后手段，且不能 destructive replace。

结论：完整性仍是产品目标，但不能以正确性为代价。

## 4. 第三个反对意见：Monotonic index 会不会保留错误数据

单纯“只增不减”也不是绝对正确。

如果旧 cache 本身已经错了，永远不允许替换会把错误永久冻结。

### 修正

Monotonicity 是默认安全策略，不是永恒真理。

允许 destructive correction，但必须需要更强 proof，例如：

- trusted capture/API 明确给出完整 authoritative snapshot；或
- candidate 覆盖全部 existing stable IDs，并额外通过 identity/version/ordering proof；或
- 用户显式执行诊断修复，并保留 rollback copy。

普通 DOM sweep 没资格做 destructive replace。

结论：把“只增不减”改成“低置信来源不可减少高置信知识”。

## 5. 第四个反对意见：Official Marker 是未公开 DOM contract

Work 12/12 很漂亮，但仍然是宿主 DOM 属性，不是公开 API。

属性未来可能：

- 改名。
- 延迟出现。
- 仅部分 surface 存在。
- 行为改变。

### 修正

OfficialMarkerBridge 永远是 capability，不是 dependency。

必须：

- runtime query。
- strict eligibility。
- 失败 no-op。
- baseline 永远存在。
- 不把 marker ID 写入长期 cache。

结论：可生产使用，但不能成为唯一导航路径。

## 6. 第五个反对意见：Observer 缩小后可能漏事件

从 body observer 缩到 conversation root 可以降成本，但宿主可能重建 root。

### 修正

使用两级 observer：

- 一个极轻量 root-lifecycle observer，只检测 conversation root 被替换。
- 一个 scoped conversation observer，监测真正需要的数据。
- scoped observer 失效时重新绑定。
- 禁止 root-lifecycle observer 执行 full Timeline scan。

结论：不能简单“把 selector 改小”，需要 observer lifecycle contract。

## 7. 第六个反对意见：拆 bootstrap.js 可能只是文件搬家

把 3300 行拆成十个 class 不等于架构改善。

### 修正

每次 extraction 必须减少跨层依赖，并用 contract 测量：

- Core 文件不得 import host/codex-desktop。
- Host adapter 不得直接修改 Core 内部 map。
- UI 不得触发 repair。
- Plugin 不得 import Host Injector。
- bootstrap/orchestrator 不得实现排序、stitch、repair 算法。

如果只是移动代码但依赖图不变，该 phase 判失败。

## 8. 第七个反对意见：Phase 0 Safety Hotfix 会不会改变稳定 v0.5.3

v0.5.3 是当前 rollback baseline，不应该悄悄重定义。

### 修正

- v0.5.3 tag 不动。
- Safety Hotfix 从新开发线开始。
- 不把新行为回填到 v0.5.3 tag。
- 每个 hotfix 都有独立 regression test。
- 实机验收失败立即回 v0.5.3。

结论：安全修复属于 v0.6 migration，不重写历史 stable。

## 9. 第八个反对意见：Plugin 可能完全帮不上 Timeline

官方 Plugin 文档当前提供 Skill/MCP/Hooks/optional UI，但没有公开当前会话 Turn tree / host navigation / permanent rail API。

所以不能把“将来 Plugin 会开放”当计划基础。

### 修正

架构必须在 Plugin 永远拿不到这些 API 的情况下仍成立。

如果未来官方开放 host extension API，只需新增 Host Adapter，不改 Core。

结论：Plugin 是机会项，不是赌注。

## 10. 第九个反对意见：是否应该直接做浏览器扩展

浏览器扩展对 Web ChatGPT 更自然，但当前项目的高价值验证来自 Codex Desktop/Work。

现在同时转 Browser extension 会：

- 扩大 surface。
- 引入两套 DOM contract。
- 分散 Chat 安全修复精力。

### 修正

v0.6 不并行做 Browser/Web 正式适配。

Core/Host 分层完成后，再评估新增 Browser Host Adapter。

结论：先解决架构，再扩平台。

## 11. Complexity Budget

为了防止“重构工程无限生长”，增加硬约束：

- 不允许同时新增两个以上新的 runtime state machine。
- Plugin PoC 不得进入 Timeline correctness path。
- legacy Chat state machine 删除量必须大于新增替代 heuristic 量。
- 每个 phase 必须能说明删除了什么职责。
- 如果 bootstrap.js 变短但总跨层状态变量增加，则不算成功。

## 12. Kill Criteria

出现以下情况应停止当前重构方向并重新评估：

1. Core extraction 需要知道 Codex DOM selector。
2. Thin Host Injector 仍必须执行 full-history automatic sweep 才能工作。
3. Plugin 成为 Timeline 正确性的必需依赖。
4. 为修一个 host selector 需要修改 Core。
5. Long Chat 仍可能从 N 自动收缩到 M<N。
6. Work baseline 因架构迁移出现新的 scroll ownership 回归。

## 13. 最强反对意见：两个 hotfix 是否已经足够

可以提出一个更保守的方案：

- 给 replaceDomSnapshot() 增加 shrink guard。
- fresh Chat 禁止 auto bootstrap。
- 保持现有架构，其余不动。

这会比 Architecture Reset 便宜得多。

### 为什么仍然不够

这两个 hotfix 可以止血，因此必须先做；但它们不能消除当前结构性风险：

- document.body 全局 observer 仍会把大量宿主 mutation 汇入同一 refresh pipeline。
- identity inference、history hydration、repair、navigation、cache persistence 仍由同一 orchestrator 协调。
- Chat “完整性”仍依赖后台滚动/采样/拼窗逻辑。
- 新的宿主 DOM 变化仍可能继续要求增加 repair heuristic。
- bootstrap.js 仍同时拥有 observation、domain mutation 和 recovery policy。

所以只做 hotfix 可以作为短期 release candidate，但不应被当作最终架构。

### 修正后的重构含义

Architecture Reset 不是“立刻重写”。

它应当是：

    Phase 0 hotfix
    -> 观察一轮实机稳定性
    -> 再逐步抽离 Core/Host
    -> 每阶段可停止

如果 Phase 0 后长期稳定，并且后续宿主变化不再推动 heuristic 增长，可以降低后续重构速度。

结论：hotfix 是第一步，也是一个真实的停损观察点；Architecture Reset 继续保留，但不是不可撤销的大工程。


## 13. 第二遍评审后的最终判断

原重构方向成立，但需要三个重要修正：

### 修正 A

不是“Hybrid first”，而是：

    Safety first
    -> Core/Host split
    -> Thin Host
    -> Optional Plugin

### 修正 B

不是绝对“只增不减”，而是：

> 低置信数据不得减少高置信知识。

### 修正 C

不把完整 Chat Timeline 目标删除。

完整性依然是目标，但获取完整性的机制必须从“后台自动 DOM 重建”迁移到“可信数据源 + 用户显式加载 + 安全增量缓存”。

综合结论：

- 不继续在现有 bootstrap 状态机上增加 repair heuristic。
- 不进行 Plugin-only 重写。
- 不进行 big-bang rewrite。
- 采用阶段式 Architecture Reset。
- 第一实施任务应该是 Chat Safety Guard，而不是 Plugin skeleton。
