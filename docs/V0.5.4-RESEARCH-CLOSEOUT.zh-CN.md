## 3. Official Marker 映射模型

研究确认：

- 官方 marker 属性：data-thread-user-message-navigation-item-id。
- raw marker ID 的第一个 UUID 可以与 GTE Turn stable ID 建立 canonical join。
- 一个 GTE logical Turn 可能对应一个或多个官方 raw markers。
- marker 数量不要求与 known Turn 数量相同。
- raw marker ID、marker DOM index、aria-label 序号、旧 HTMLElement 都不能视为稳定身份。

生产候选模型必须是：

    Turn stable ID
    -> 当场扫描当前 official markers
    -> canonical Turn -> marker[]
       -> 1 个：fast-path candidate
       -> 0 个：baseline
       -> >1 个：ambiguous，baseline

不得猜测、不得缓存旧 marker element、不得恢复 Fiber / L3 deep scan。

## 4. Chat Research 暂停原因

### CHAT-START-STALL-001

实机现象：

- 新建普通 Chat。
- 第一问提交后界面卡住数秒。
- 随后恢复。

源码审查发现高风险路径：

- GPT TalkEnhancer 在 document.body 上观察 childList + subtree + attributes。
- mutation 会调度 refresh。
- 新 Chat 第一问出现时，空/小 index 可能进入 Chat true-top bootstrap。
- Chat boundary hydration 默认等待 1800 ms，bootstrap 可容忍 2 次 boundary stall。

这与“第一问后卡几秒”的时间尺度一致，但尚未完成实机因果证明，所以当前记为高可信候选根因，不写成最终结论。

### CHAT-REPAIR-COLLAPSE-001

实机现象：

- 一个约 102Q 的普通 Chat 长时间显示“正在修复时间线”。
- 修复后期 Timeline 错误收缩到约 5Q。

源码审查确认存在破坏性风险链：

    repairExistingChatIndex
    -> stitched / sweep snapshot
    -> replaceDomSnapshot(snapshot)
    -> records.clear()
    -> merge snapshot
    -> persistTimelineCache()

当前 isValidCompleteDomSnapshot() 只验证 candidate 自身 ID/order 唯一并且 order 为 0..N-1 连续，不能证明 candidate 覆盖原有完整 Timeline。

因此，一个内部自洽但只有少量 Turn 的 snapshot，有可能覆盖一个更大的既有 DOM-only index。

这是架构级安全缺口，不再继续通过增加 heuristic 扩展自动 repair。

## 7. 转入 v0.6 的硬要求

v0.6 必须先解决架构职责问题，再恢复产品功能开发。

最低硬约束：

1. Timeline knowledge 默认只增不减。
2. destructive replacement 必须证明 candidate 至少覆盖已有 stable IDs。
3. 新 Chat 不得因为“确认没有历史”自动执行重型历史探测。
4. 正常 Chat 不得自动执行不透明的全量 sweep + replace。
5. DOM observation 必须缩小作用域。
6. Host DOM 适配层不得继续承担完整会话数据库职责。
7. Plugin 不能被假设拥有未公开的宿主会话/导航 API。

详细方案见 V0.6-ARCHITECTURE-RESET.zh-CN.md。
