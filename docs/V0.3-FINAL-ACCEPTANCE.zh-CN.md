## 1. 最终结论

GPT TalkEnhancer 0.3 Desktop 的两个核心产品能力已完成当前阶段验收：

1. **Conversation Timeline / Question List**
2. **Prompt Picker / Prompt Library**

其中最关键的长对话 Navigation 已经过真实 Codex Desktop 手动压力测试：

```text
Q1 → Q76：多次 PASS
Q76 → Q1：多次 PASS
```

此前在 Q1 ↔ Q37 测试中出现的“远距离跳转停在半路、再次点击后继续”问题，最终定位为旧 Navigation 使用固定总预算：

```text
maxHydrationSteps = 64
maxNavigationMs   = 12000
```

长对话虚拟化仍在持续加载和前进时，TalkEnhancer 会因为自身预算耗尽而提前返回 `target-not-hydrated`。

最终方案改为 **progress-renewed navigation budget**：只要导航仍产生真实进展，就刷新活跃预算；固定 12 秒不再作为正常终止条件。

当前安全边界：

```text
持续无进展约 5 秒                    → navigation-inactive
连续 hydration stall                 → hydration-stalled
绝对熔断：约 256 probes / 45 秒      → navigation-hard-limit
新 Qxx 点击                          → supersede 旧导航
```

因此当前 0.3 Navigation 可视为本阶段冻结基线，不建议继续无证据地调整步长、等待时间或视觉参数。

## 5. 真实 Codex Desktop DOM 事实

### 5.1 Conversation identity

ChatGPT 会话可通过侧栏稳定 key 识别：

```text
data-sidebar-chatgpt-conversation-key="chatgpt:conversation:<UUID>"
```

固定项目/本地 Thread 某些 UI 只暴露标题、`aria-current="page"` 和 React 临时 ID，没有稳定 conversation UUID。0.3 对这种情况保持 fail-closed，不使用标题或 `_r_*` 临时 ID 伪造 ConversationStore identity。

### 5.2 User Turn

当前 Desktop 已确认使用：

```text
[data-markdown-text-tone="user-message"]
[data-content-search-turn-key="fallback-turn-N"]
[data-turn-key="fallback-turn-N"]
```

没有可直接读取的隐藏真实 UUID 时，`fallback-turn-N` 的 N 可作为用户 Turn 的顺序桥接。

### 5.3 Virtualizer / Scroll

真实滚动容器已确认：

```text
flex-direction: column-reverse
scrollTop 可为负数
```

因此 0.3 使用 top-origin logical scroll model，而不是直接用 raw `scrollTop` 做业务定位。

真实长会话只在 DOM 中保留一个有限虚拟窗口，例如：

```text
fallback-turn-31 ... fallback-turn-36
```

随着真实/程序化滚动，窗口才继续 hydrate。

## 6. Navigation 最终模型

最终 Navigation 不再使用单次 percentage jump，也不把 viewport `top + 120` 当作全局激活线。

### 6.1 激活坐标系

Active / align 统一使用：

```text
scrollContainer.getBoundingClientRect().top + activationOffset
```

而不是 browser viewport 的绝对 120px。

### 6.2 未渲染 Turn

远距离定位流程：

```text
target order
→ 判断 target 位于当前 fallback window 前/后
→ 分段 logical scroll
→ 等待虚拟化 hydration
→ 观察 progress
→ target DOM 出现
→ 精确几何对齐
→ post-settle 稳定确认
```

Hydration progress 包含三类：

1. `fallback-turn` 可见范围向目标靠近；
2. `scrollHeight / maxLogicalPosition` 扩大，表示 Codex 新历史块被加载；
3. `logicalPosition` 持续向目标移动，表示正在穿过长回答内容。

只有三类进展均停止，才允许计入 stall。

### 6.3 Progress-renewed budget

旧问题：

```text
Q37 → Q1
Q37 → Q28 → Q19 → Q11 → Q5
此时仍有进展，但固定 12 秒预算耗尽
→ target-not-hydrated
```

新模型：

```text
真实进展
→ 刷新 lastProgressAt
→ 继续导航
```

正常导航不会因为总耗时超过旧 12 秒就失败。

### 6.4 Post-settle verification

目标进入 DOM 且首次对齐成功后，不立即返回 `ok`：

```text
align
→ settle
→ verify
→ 若异步 reflow / scroll drift
→ 再校正
→ 再验证
```

防止“某一帧到了目标，但稍后又漂走”的假成功。

### 6.5 Debug

`window.__GPTTalkEnhancerDebug.navigation` 当前保留：

```text
reason
probes
stalls
elapsedMs
inactiveMs
budgetLimit
visibleRange
scrollHeight
maxLogicalPosition
logicalPosition
domId
settleChecks
```

后续 Codex 更新导致 Navigation 回归时，应先读取这些字段再决定是否修改算法，不建议先调参数。

## 9. Conversation Capture 结论

0.3 允许唯一一种窄范围只读网络捕获：

```text
GET /backend-api/conversation/{conversationId}
```

实现要求：

- 先调用原始 fetch；
- 返回原始 response；
- 仅异步读取 `response.clone()`；
- 不修改请求；
- 不修改响应；
- 不读取 token / credentials。

真实 Codex Desktop 中，即使 wrapper 从 new-document 阶段已激活，也没有观察到稳定的该 GET 页面 fetch。因此：

```text
capture.status = active
capture.turnCount = 0
health 可能 = degraded
```

这不是注入失败，而是当前 Desktop 数据路径不经过允许的页面 fetch。

0.3 不为补齐 Capture 而接入 Codex 内部 RPC、数据库或 React 私有状态。Timeline 必须允许无 Capture 的 Progressive DOM 模式正常工作。

## 13. 已知限制

### 13.1 Capture 无完整数据

当前 Codex Desktop 不稳定触发允许的 conversation GET fetch，所以无法保证打开一条从未浏览过的超长会话时立刻拥有完整 Question Overview。

TurnIndex 会随着 DOM hydration / 用户浏览 / Navigation 持续积累已发现 Turn。

### 13.2 Host selector contract 可变化

Codex Desktop DOM 是外部宿主契约，未来版本可能改变：

- sidebar conversation key
- user-message selector
- fallback turn attributes
- scroll container class / structure
- Composer anchor

出现回归时优先读取 Debug 与真实 DOM，不根据旧 selector 盲修。

### 13.3 Stable identity fail-closed

如果某类侧栏 Thread 没有稳定 UUID，只暴露标题或 React 临时 ID，0.3 不使用这些不稳定值创建 Conversation identity。

### 13.4 Full Scan 不属于 0.3 产品

验收阶段可用模拟/滚动诊断验证虚拟化行为，但正式产品不在后台自动扫描整个会话。

- Prompt visual / positioning

- Navigation progress model
- Progress-renewed budget
- Post-settle verification
- Codex++ two-file loader layout

不建议继续为“可能更快一点”调整 Navigation 步长或超时。当前优先级应从“继续修 0.3”转向版本整理、发布准备或 0.4 设计。

## 15. 0.4 建议方向

0.4 如继续演进，优先级建议：

1. **Clean-room / GPL 边界整理**：若希望降低 GPL 派生代码影响，可重写 Timeline / Question List 参考实现。
2. **Host contract observability**：继续完善 selector / virtualizer diagnostics，而不是接私有 RPC。
3. **Conversation identity coverage**：仅在宿主提供稳定 ID 时扩展 Codex local/project Thread 支持。
4. **Navigation UX**：可增加轻量“定位中”状态，但不要改变已经稳定的核心导航模型。
5. **Browser path**：如果继续支持 Vivaldi / Chrome，应与 Desktop Host 分离验收，不让浏览器路径反向绑架 Desktop 架构。

不建议 0.4 直接引入：Cloud Sync、Folder/Tags、Token/Model 管理或复杂 Native Bridge，这些会显著扩大产品边界。
