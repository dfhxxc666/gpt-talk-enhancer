### Marker 生命周期与映射模型

实测确认 raw marker 不是稳定的一对一集合：

- 初始可见为 64 raw / 64 canonical / 0 duplicate canonical。
- 历史 hydration 后可增长到 67 raw / 64 canonical / 3 duplicate canonical。
- 某些 raw ID 从 <turnUUID>:0:user 演化为 <turnUUID>:<messageUUID>。
- 同一个 canonical Turn 可能对应多个不同 raw markers。

因此正式 bridge 不得缓存 marker DOM index、aria-label 序号、完整 raw marker ID 或旧 HTMLElement。

当前可接受的 join key 是 raw ID 的第一个 UUID，即 GTE Turn stable ID，但映射必须按：

    Turn stable ID
    -> 当前 DOM 即时查询
    -> marker[]
       -> 1 个：fast-path candidate
       -> 0 个：baseline
       -> >1 个：ambiguous，baseline

markerCount === knownTurnCount 不是正确性条件。

### 当前架构判断

Official Marker Direct Bridge 继续作为 v0.5.4 第一优先级候选。

正式实现若进入 runtime，应保持薄层：

    Timeline target
    -> NavigationStrategyGate
    -> OfficialNavigationBridge
       -> exact canonical Turn
       -> 当前 marker count === 1
       -> marker.click()

- 固定 Q -> scrollTop 数据库

## 1. 当前结论

v0.5.4 暂不实现正式 fast path。

第一优先级改为研究官方 Work message navigation rail 是否能被 Codex++ 注入直接复用。

截图所指的“官方 Work 快路径”是官方右侧 message navigation rail，而不是 GPT TalkEnhancer 当前的 Work wheel hydration。

如果官方 marker 的 programmatic click 能稳定触发宿主自己的 virtualizer/navigation controller，那么 GPT TalkEnhancer 有机会通过一个很薄的 OfficialNavigationBridge 接近官方导航速度，而不需要重做整个架构。

如果该入口不可复用，再退回 Sparse Navigation Hint Cache 等方案。

## 2. 已有历史证据

历史 v0.5.2 研究确认过：

- 官方 Work rail DOM 存在 data-thread-user-message-navigation-item-id。
- 某稳定状态出现 official markers=64、known turns=63、mapped turns=63、coverage=1、conflicts=0。
- 某宿主重建状态出现 official markers=67、known turns=63、best coverage=0.952、conflicts=3、oneToOne=false。
- 因此 exact marker identity 有研究价值，但 marker index 不能当永久 turn order。
- Fiber / key-join deep scan、post-navigation rescan、mutation-driven recovery 曾造成真实 Codex Desktop 主线程明显卡顿，因此自动运行路线继续冻结。

重要：以上只证明历史上曾能建立高覆盖 mapping，不证明 programmatic marker click 已验证。

## 3. 新发现

复核旧 official-navigation-probe、official-navigation-auto-map、host-internal-depth-probe 后，未发现已经正式执行并验证以下动作的证据：

- HTMLElement.click() 直接点击 official marker。
- synthetic MouseEvent sequence。
- synthetic PointerEvent sequence。

因此 v0.5.4 最优先实验应该从最便宜的 DOM direct action 开始，而不是重新进入 Fiber。

## 4. 候选方案优先级

### A0：Official Marker Direct Bridge

目标：按 target turn stable ID 找到唯一 official marker，然后调用最小成本官方动作，再由 v0.5.3 baseline verify。

理想链路：

GPT TalkEnhancer target turn
→ exact official marker by stable ID
→ official marker action
→ host virtualizer/navigation
→ target mounted
→ v0.5.3 verification

Official Bridge 只负责加速，不负责定义正确性。

找不到 exact marker、mapping 不唯一、identity 不稳定、Timeline unhealthy 或 scroll owner 非 idle 时，直接 baseline。

### A1：Official Marker Capability Research

先只测量，不接 Timeline 正常点击：

- Work marker 是否稳定存在。
- marker ID 是否与 TurnIndex stable ID exact match。
- marker count / lifecycle 在 lazy load、thread switch、restart 后如何变化。
- 官方人工点击的 click-to-first-scroll、click-to-window-change、click-to-verified-target。
- Chat / Pinned / Project / Mobile Chat 是否存在同类 marker。

### B：Sparse Navigation Hint Cache

只有官方 marker 不可复用或 Chat 无官方入口时再优先研究。

原则：只保存稀疏位置提示，不作为 truth source；只允许 one-shot coarse seek，最终仍由 v0.5.3 baseline verify。

首轮只做 memory/session cache。没有数据证明稳定前不做 persistent database，不上 IndexedDB。

### C：Dynamic Binary Seek

无持久缓存对照组。利用 targetOrder、visibleRange、logicalPosition、maxLogicalPosition 做动态区间缩小。

### D：Work-style Chat Wheel

最后评估。学习 Work 的闭环 evidence/progress，而不是机械复制 wheel 参数。

## 5. A0/A1 实验顺序

### R0：Manual Observation

只观察用户手动点击官方 Work rail，不触发 GPT TalkEnhancer 快路径。

至少覆盖 3 个 Work conversations、20 次官方 marker 点击。

记录：

- markerCount。
- marker stable ID。
- knownTurnCount。
- exactIdMatch。
- targetOrder。
- before/after visible range。
- before/after logical position。
- before/after scrollHeight。
- clickToFirstScrollMs。
- clickToWindowChangeMs。
- clickToVerifiedTargetMs。
- scrollEventCount。
- containerChanged。

R0 要回答：marker stable ID 是否能在多个 thread / lifecycle 状态中可靠对应 TurnIndex。

### R1：One-shot Programmatic Click

只有 R0 通过后才增加手动 research probe。

尝试顺序：

1. HTMLElement.click()。
2. 必要时 synthetic MouseEvent sequence。
3. 必要时 synthetic PointerEvent sequence。

如果全部失败，停止 Official Direct Bridge 路线，不立即转 Fiber。

至少 20 次 programmatic marker action，跨至少 3 个 Work conversations。

要求：

- verified target success=100%。
- wrong target=0。
- scroll oscillation=0。
- Timeline/cache/order corruption=0。

同时记录 median 与 p95 的 click-to-verified-target。

### R2：Chat Capability Check

只检查普通 Chat、Pinned Chat、Project Chat、Mobile-created Chat 是否存在同类 official marker 及 exact ID mapping。

如果 Chat 不存在 official marker，不通过 Fiber 强行制造 mapping，转 B/C 方案。

## 6. 架构判断

如果 A0 成功，不需要重做 GPT TalkEnhancer。

建议只增加：

- NavigationStrategyGate。
- OfficialNavigationBridge。
- OfficialNavigationDiagnostics。

v0.5.3 Chat / Work NavigationAdapter、TurnIndex、TimelineCache 全部保留。

Official Bridge 必须是薄层：成功则缩短导航，失败立即回 baseline；不能成长成第二套完整导航控制器。

## 7. 必须继承的 v0.5.2 / v0.5.3 教训

- 不把 Fiber / L3 deep scan 挂回正常 Timeline 点击。
- 不做 post-navigation 自动深扫。
- 不做 mutation-driven deep recovery。
- fast path 不确定时立即 baseline，不叠加更重 recovery。
- 一个时刻只能有一个 scroll owner。
- Timeline order health 必须 healthy。
- cache restore 不能处于 rejected / pending repair。
- conversation identity 必须 stable。
- scrollOwnership.owner 必须 idle，conflict 必须 false。

## 8. Local Navigation Hint Cache 的当前判断

方向合理，但暂时降为 Plan B。

不建议做固定 Q→scrollTop 数据库，因为虚拟列表 extent、history loading、viewport、assistant 内容高度都会导致坐标漂移。

如果进入 Plan B，优先研究 sparse anchors + logical position ratio + geometry epoch + confidence，而不是每个 Q 固定坐标。

数据量很小，首轮 memory / 现有 StorageAdapter 足够，不需要 IndexedDB。

## 9. 构建门禁

0.5.4 禁止“先实现再找数据证明”。

Official Marker 路线：先完成 R0，再决定是否写 R1 probe；R1 通过后才讨论正式 strategy integration。

Hint Cache 路线：必须先有真实 navigation dataset 和 shadow predictor 证明 order→position 关系有稳定预测价值，才允许实现 session cache。

任何候选进入正式运行时前必须满足：

- verified correctness=100% on critical real-machine matrix。
- wrong conversation=0。
- wrong Q=0。
- Timeline corruption=0。
- visible scroll oscillation=0。
- median 相对 v0.5.3 baseline 改善目标至少约 25%。
- p95 不允许明显退化。
- fallback 后 baseline 仍能完成导航。

## 10. 当前未验证项

以下全部仍为未验证假设：

- programmatic .click() 是否能触发官方 Work navigation。
- synthetic event 是否被宿主接受。
- Chat 是否存在同类 official marker。
- Official Marker Bridge 是否能达到官方手动点击同级速度。
- Sparse Navigation Hint Cache 是否具有足够稳定的 geometry 关系。

在取得真实数据前，不得把任何一项写成已实现或已通过。
